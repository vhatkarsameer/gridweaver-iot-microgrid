## 5. Telemetry Data Model

Telemetry represents the current information generated by an IoT device.

The existing `TelemetryPayload` is implemented as a Java record.

It contains the following fields:

| Field | Type | Description |
|---|---|---|
| `deviceId` | `String` | Unique device identifier |
| `deviceType` | `DeviceType` | Type of IoT device |
| `status` | `DeviceStatus` | Current device status |
| `outputWatts` | `double` | Power generated or transferred |
| `batteryLevelPct` | `double` | Battery charge percentage |
| `latitude` | `double` | Household/device latitude |
| `longitude` | `double` | Household/device longitude |
| `timestamp` | `Instant` | Time when telemetry was generated |

### Example Telemetry

```json
{
  "deviceId": "SOLAR-HOUSE-MUM-1000",
  "deviceType": "SOLAR_PANEL",
  "status": "GENERATING",
  "outputWatts": 150.0,
  "batteryLevelPct": 0.0,
  "latitude": 19.076,
  "longitude": 72.8777,
  "timestamp": "2026-08-19T06:09:07.478754600Z"
}
```

### Telemetry Fields

#### Device ID

Identifies the simulated device.

Example:

```text
SOLAR-HOUSE-MUM-1000
BATT-HOUSE-MUM-1000
```

#### Device Type

Identifies whether the telemetry belongs to a solar panel or battery.

```text
SOLAR_PANEL
BATTERY
```

#### Device Status

Represents the current state of the device.

```text
IDLE
GENERATING
CHARGING
FAULT
DISCHARGING
```

#### Output Watts

Represents the power generated by a solar panel or transferred by a battery.

#### Battery Level

Represents the battery charge percentage.

For solar panels, the simulator currently uses:

```text
0.0%
```

#### Location

The latitude and longitude identify the household/device location.

#### Timestamp

The timestamp records when the telemetry was generated.

## 6. Household Location

The `HouseholdLocation` record represents the geographical location of a household.

It contains:

```text
houseId
latitude
longitude
```

Example:

```text
HOUSE-MUM-1000
Latitude: 19.0760
Longitude: 72.8777
```

The household location is associated with the simulated devices belonging to that household.

Each household has its own location, and both the solar panel and battery associated with that household use the same location.

## 9. IoT Simulator

The existing `IotSimulatorService` is responsible for generating simulated telemetry.

The simulator starts when the Spring Boot application becomes ready through the `ApplicationReadyEvent`.

It performs the following operations:

1. Creates household locations.
2. Creates a solar device for each household.
3. Creates a battery device for each household.
4. Runs the simulated device tasks using Java virtual threads.
5. Generates telemetry periodically.
6. Publishes telemetry to the WebSocket topic.

The simulator uses:

```java
Executors.newVirtualThreadPerTaskExecutor()
```

This allows a large number of simulated device tasks to run concurrently.

---

## 10. Simulated Households

The simulator creates 5,000 household locations.

Household IDs follow the format:

```text
HOUSE-MUM-<number>
```

Examples:

```text
HOUSE-MUM-1000
HOUSE-MUM-1001
HOUSE-MUM-1002
```

The simulator uses the following base geographical location:

```text
Latitude: 19.0760
Longitude: 72.8777
```

Random variation is applied around this base location to distribute households across the simulated area.

The generated household locations are stored in:

```java
List<HouseholdLocation>
```

---

## 11. Simulated Devices

Each household receives two simulated devices:

```text
1 Solar Panel
1 Battery
```

Therefore:

```text
5,000 households
       ×
2 devices
       =
10,000 simulated device tasks
```

The resulting structure is:

```text
Household
   |
   +---- Solar Panel
   |
   +---- Battery
```

The device IDs are generated using the household ID.

Example:

```text
SOLAR-HOUSE-MUM-1000
BATT-HOUSE-MUM-1000
```

## 14. WebSocket Configuration

The existing backend uses Spring WebSocket with STOMP messaging.

The WebSocket endpoint is:

```text
/ws-grid
```

Clients use this endpoint to establish a WebSocket/STOMP connection.

The application uses the following messaging configuration:

```text
Application destination prefix:
/app

Message broker prefix:
/topic
```

Telemetry is published to:

```text
/topic/telemetry
```

---

## 15. WebSocket Communication Flow

The existing Week 1 communication flow is:

```text
IoT Simulator
      |
      v
TelemetryPayload
      |
      v
SimpMessagingTemplate
      |
      v
STOMP Message Broker
      |
      v
/topic/telemetry
      |
      v
Connected WebSocket Client
```

A client first connects to:

```text
/ws-grid
```

and then subscribes to:

```text
/topic/telemetry
```

After a telemetry message is published, connected subscribers can receive the telemetry payload.

---

## 16. WebSocket Transport Configuration

The existing `WebSocketConfig` configures additional WebSocket transport limits.

The configured values are:

| Configuration | Value |
|---|---:|
| Message size limit | 512 KB |
| Send buffer size limit | 10 MB |
| Send time limit | 20 seconds |

These settings provide additional capacity for the simulated telemetry stream.

### Message Size Limit

```text
512 KB
```

Defines the maximum allowed size of an individual WebSocket message.

### Send Buffer Size Limit

```text
10 MB
```

Defines the maximum amount of data that can be buffered for sending.

### Send Time Limit

```text
20 seconds
```

Defines the maximum amount of time allowed for sending a WebSocket message.

## 17. Telemetry Broadcasting

The simulator uses Spring's `SimpMessagingTemplate` to broadcast telemetry.

The existing implementation sends the generated payload to:

```text
/topic/telemetry
```

The communication flow is:

```text
IotSimulatorService
        |
        | Generate payload
        v
TelemetryPayload
        |
        | convertAndSend()
        v
/topic/telemetry
        |
        v
WebSocket Clients
```

The relevant existing operation is:

```java
messagingTemplate.convertAndSend("/topic/telemetry", payload);
```

No additional telemetry processing service is introduced as part of Week 1.

## 27. Java Runtime Configuration

The project targets Java 21.

The IoT simulator uses Java 21 virtual threads:

```java
Executors.newVirtualThreadPerTaskExecutor()
```

Therefore, Java 21 should be used when running the Week 1 backend and test suite.

The recommended environment is:

```text
Java 21
Maven Wrapper
Spring Boot
```

### Java Compatibility

The project should be tested using the configured Java version.

Using a newer unsupported JDK can result in compatibility problems with testing dependencies such as Mockito and Byte Buddy.

Therefore, the Week 1 test environment should use Java 21.
