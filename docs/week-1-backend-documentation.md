## 4. Backend Architecture

The backend processes IoT telemetry through several components.

### High-Level Flow

```text
IoT Simulator
      |
      v
TelemetryService
      |
      v
TelemetryStateProcessor
      |
      v
TelemetryWebSocketService
      |
      v
STOMP Message Broker
      |
      v
/topic/telemetry
      |
      v
WebSocket Client
```

The purpose of this pipeline is to allow telemetry generated by simulated IoT devices to be processed by the backend and made available to connected clients in real time.

---

## 5. Telemetry Data

Telemetry represents the current state and measurements of an IoT device.

The telemetry payload contains information such as:

* Device ID
* Device type
* Device status
* Power output
* Battery level
* Latitude
* Longitude
* Timestamp

Example telemetry used during testing:

```json
{
  "deviceId": "TEST-SOLAR-001",
  "deviceType": "SOLAR_PANEL",
  "status": "GENERATING",
  "outputWatts": 150.0,
  "batteryLevelPct": 0.0,
  "latitude": 19.076,
  "longitude": 72.8777,
  "timestamp": "2026-08-19T06:09:07.478754600Z"
}
```

## 6. IoT Simulator

The backend contains an IoT simulator used to generate simulated device activity.

The simulator represents multiple IoT households/devices and produces telemetry that can be processed by the backend.

The Week 1 test environment also supports disabling the simulator when deterministic integration testing is required.

Example test output:

```text
[TEST MODE] IoT simulator disabled.
```

This allows integration tests to provide controlled telemetry instead of relying on continuously generated simulator data.

## 7. WebSocket Configuration

The backend uses Spring's WebSocket and STOMP support.

The WebSocket endpoint is:

```text
/ws-grid
```

Clients connect to this endpoint to establish a WebSocket/STOMP session.

Telemetry is published through:

```text
/topic/telemetry
```

The general communication flow is:

```text
Client
  |
  | WebSocket connection
  v
/ws-grid
  |
  | STOMP
  v
Message Broker
  |
  | subscription
  v
/topic/telemetry
```

---

## 8. WebSocket Communication

The Week 1 implementation verifies real WebSocket communication rather than only testing individual methods.

The integration test performs the following sequence:

1. Start the Spring Boot application.
2. Start an embedded Tomcat server on a random port.
3. Connect a STOMP client to `/ws-grid`.
4. Establish the WebSocket connection.
5. Subscribe to `/topic/telemetry`.
6. Create a test `TelemetryPayload`.
7. Send telemetry through the telemetry service.
8. Process the telemetry through the state-processing boundary.
9. Publish telemetry through the WebSocket service.
10. Broadcast the telemetry through the STOMP broker.
11. Receive the telemetry on the WebSocket client.
12. Verify the received payload.
13. Close the WebSocket session.

## 11. Java and Maven Configuration

The project is configured to compile against Java 21.

During testing, an issue was identified where Maven tests were initially executed using Java 25.

This caused Mockito/Byte Buddy compatibility errors because the Byte Buddy version used by the project did not officially support Java 25.

The error was:

```text
Java 25 (69) is not supported by the current version of Byte Buddy
which officially supports Java 22 (66)
```

The test environment was corrected to use JDK 21, which matches the project's configured Java release.

After correcting the Java runtime:

```text
Tests run: 4
Failures: 0
Errors: 0
Skipped: 0

BUILD SUCCESS
```
